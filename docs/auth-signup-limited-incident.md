# Supabase Test signup delivery incident

Scope: `ezlycwkuzkwcnhrhiruv` and the isolated FILMATTA Auth Preview.
Production and staging were not changed.

## Observed failure

The public `/registro` form invokes the `signUp` Server Action in
`app/auth/actions.ts`. FILMATTA's own `allowAuthAttempt("signup", email)` gate
runs first. For the observed failed requests, execution reached
`supabase.auth.signUp()`: Vercel Preview runtime logs recorded the returned
Supabase code `over_email_send_rate_limit` with HTTP 429 at 2026-10-09
01:20, 01:25 and 01:27 UTC. The application then redirected to
`/registro?error=signup_limited`. No account address or token appeared in
those logs.

## Root cause

The Supabase Test dashboard showed **Enable custom SMTP: off**. Its actual
**Rate limit for sending emails** was **2 emails/hour**. The visible
**30/hour** figure was the SMS limit; it was not the email quota. No Send Email
Hook was configured. Public signup and email confirmation remained enabled.
The `over_email_send_rate_limit` response was therefore generated by
Supabase Auth before any handoff to Resend. Waiting one minute cannot clear
an hourly quota. No change to the FILMATTA IP budget or Supabase rate limits
is warranted by this evidence.

The first version also used `signup_limited` for FILMATTA's own pre-Supabase
budget and treated every provider HTTP 429 as an email quota. The repair
separates those cases. Server logs record a fixed source marker, status, code,
type and a tightly constrained safe message. User-facing pages display only
human-readable feedback codes.

## Supabase Test repair

The project owner entered the authorized Resend credential directly in
Supabase Test. After reload, the dashboard showed Custom SMTP **on**, host
`smtp.resend.com`, port `465`, sender name `FILMATTA`, and the email rate limit
at **30/hour**. The credential was not copied to this repository or local files.
The Test confirmation and recovery templates were saved with the token-hash
links in `docs/public-signup-auth-gate.md`, and their contents persisted after
reload. These settings apply to Test only.

A fresh public UI signup must still prove that Supabase accepts the request,
Resend receives it, the inbox receives the confirmation, and the callback
creates a valid session. The Create → Project → Writer and recovery journeys
follow that proof; do not infer delivery from the SMTP switch alone.
